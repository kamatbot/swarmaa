Recommendation: reuse Reason for live-agent discovery and message delivery. Build a companion service that owns shared memory, durable tasks, artifacts, and authorization. Connect Dot and Grok Bot to the same service as equal entry points.

This gives the desired experience: start work in Dot, let Codex or Claude execute it, involve Antigravity when appropriate, and later continue in Grok without reconstructing the task from chat history.

1. The experience to build

Dot and Grok should each understand what the network knows, which tasks are active, and what another agent has already produced. A user should be able to ask either one to continue work, inspect evidence, or delegate a bounded part of a task.

Example target workflow: “Dot, investigate the OpsOdds signal issue and ask Codex for a proposed fix. Have Claude review the reasoning. Save the decision and patch.” Later: “Grok, what did the network conclude, and what is ready for me to review?”

The second question should return the same task, revision, evidence, and artifacts created by the first workflow. It should distinguish a proposed patch from a validated or deployed change. If Grok requests further work, it should append an instruction to that task rather than start an independent competing job.

Use capability-based roles. Dot and Grok handle conversation, planning, research, and results; Codex and Claude provide coding/review capabilities; Antigravity contributes its configured development and browser capabilities. These are defaults, not claims that a particular model is universally best at a role. Each client may both contribute to memory and use it.

Scope the first pilot to project work. Your wider personal and family knowledge can be added later with its own permissions. Existing FamETC parent-governed memory should remain under FamETC’s approval rules if it is ever connected.

2. What the repository provides

Reason is a Rust daemon with MCP tools and agent adapters. Its public documentation presents it as a directory and message bus, and the source confirms that boundary. It offers a useful foundation for reaching existing sessions across machines. [1] [2]

The persistence limits matter

The store is designed around message/session lifetimes. Undelivered outbox entries age out after seven days. Stale non-CLI sessions are normally forgotten after roughly a day, with unread non-held mail removed. Attached files also expire. These are intentional transport policies, not bugs. [3]

Therefore a durable task must be written to the new database before Reason sends its notification. Reports, patches, decisions, and checkpoints must be stored independently of a Reason inbox. The source’s delivery path permits redelivery; receiving or reading a message cannot be treated as executing its requested action. [4]

The hosted bridge is a separate component

The local daemon supervises the external command reason network __relay. The public hosted HTTP MCP service is not implemented by this engine’s stdio MCP module. A clone of this repository therefore does not supply the entire hosted-assistant stack. [5]

For a pilot, use the existing hosted bridge and add the shared memory/task endpoint. For an owned deployment, implement a narrow authenticated gateway and Mac bridge. Hosting an iroh relay alone would not replace the HTTP MCP gateway or its authentication.

Trust boundary: Reason documents encrypted computer-to-computer traffic, while hosted-assistant messages pass through its server. The shared memory service and model providers also receive the context sent to them. The complete system must be described according to those actual paths, rather than inheriting an end-to-end privacy claim from the peer transport. [6]

Antigravity adapter: concrete scope

Use its real conversation ID, project paths, and installed surface to register a logical worker. On session start, retrieve a bounded context packet. At suitable lifecycle points, check task updates and capture selected evidence. A stop event should create a checkpoint; only a completed result satisfying task criteria should close the task.

Use documented headless workers for unattended jobs. An enabled App sidecar is another path for sending messages into existing App conversations. Do not assume the same facility exists in the IDE or that a generic MCP connection can wake an idle conversation.

Current Antigravity remote MCP configuration uses serverUrl. A future endpoint could be registered as follows; the address is an illustrative placeholder, not a deployed service. [13]

{
  "mcpServers": {
    "collective-memory": {
      "serverUrl": "https://YOUR-SERVICE/mcp"
    }
  }
}

Authentication and scope assignment belong in setup. Reuse the host’s supported authentication flow; do not place a shared master credential in checked-in configuration.

Notifications to both access points

Publish concise task-change events containing an event ID, task ID, revision and status. The receiving bot fetches authorized content from the shared service. Persist event delivery attempts and deduplicate retries. A successful notification delivery is not evidence that a user read it or that a worker completed a task.

Dot’s current documented path uses MCP Events with protocol 2026-07-28, persistent subscriptions and verified webhook delivery. Grok uses a webhook routine. These are separate adapters over the same task-event outbox. Actual account controls and end-to-end delivery must be checked during setup. [7] [9]

Reference stack: one TypeScript service, one PostgreSQL database, and object storage for artifacts. Start with structured filtering and full-text search. Add vector retrieval when real recall examples demonstrate a need. Keep the queue and event outbox in the database initially, so task creation and notification intent can commit together.

The service is the authority; the model chosen to plan a task can vary. Dot and Grok do not need separate coordinator databases or separate copies of memory. Avoid a vector database, a graph database, a message broker, and a multi-master replication system before the first useful workflow works.

A Mac-only service is a possible deployment variant, but it makes both hosted entry points depend on the Mac and home connection. For the intended everyday experience, cloud state with local execution is the stronger default. No additional cloud account or hosting plan has been selected or purchased.

Reason daemons operate within an OS user’s environment. On your Macs, configure the actual accounts that run the agents, and map each bridge explicitly. Do not assume an agent in one logged-in account can see the sessions or credentials of another. [2]

5. Collective-memory contract

Collective memory should store reusable knowledge with evidence and revision history. It should give an agent the relevant current context for a task, while retaining where that context came from.

Record categoryExamplesWrite/read behavior
Preferences and constraintsPreferred response format; a project’s standing deployment restriction.Promote from attributable user input; distinguish preferences from enforced tool permissions.
Project decisionsCalendar-first dashboard; accepted architecture; rejected feature.Keep decision rationale, source, effective date and superseded version.
Observed factsRepository revision inspected; version installed; outcome returned by a tool.Store the observation’s evidence and time; set expiry where the fact can change.
ProceduresHow to reproduce a failure or perform an authorized local workflow.Record scope, prerequisites, last successful use, and owner.
Proposals and hypothesesAn agent’s diagnosis or suggested architectural choice.Remain labeled as proposals until supporting evidence or an explicit decision changes their status.

Task checkpoints belong to the task ledger and can reference memory records. Large documents, code patches and logs belong in artifact storage. This avoids turning every token of a conversation into an equally authoritative “memory.”

Minimal record model

MemoryRecord
  id, tenant_id, scope, kind, subject, key, value
  status: proposed | active | disputed | superseded | retracted
  version, supersedes_id
  source_actor, source_event_or_task, evidence_refs
  observed_at, valid_from, expires_at
  sensitivity, retrieval_policy

MemoryRevision
  memory_id, version, prior_version, change_reason, actor, timestamp

MemoryEvidence
  source_id, original_source_id, artifact_ref, excerpt_or_locator

A useful example is a dashboard requirement that regular school classes remain hidden while ECAs appear. An agent proposing a UI change should see that requirement, its source, and the project scope. The system should not infer a new enduring preference merely because a screenshot or temporary experiment differs.

Write policy with low friction

  1. Write routine execution evidence automatically. A task’s observed commit, generated artifact checksum and checkpoint need no repeated user confirmation.
  2. Separate verified source from agent assertion. A tool call by Dot proves which client made the call; it does not by itself prove the payload contains a human instruction. Record an attributable user message reference when available; otherwise label the claim as agent reported.
  3. Use version checks for updates. A write supplies the version it read. Conflicting assertions remain visible rather than silently replacing each other.
  4. Give direct user corrections priority in the knowledge model. Preserve the prior revision for explanation, but retrieve the corrected active record.
  5. Count original evidence. Three agents repeating one guess are not three independent confirmations. Preserve a common original-source ID.
  6. Keep tool authorization in a separate policy store. Memory saying “deployments are approved” cannot grant deployment access. Existing authority can be reused; new authority must come through the correct user/action path.

Use project scopes such as project:opsodds and project:fametc, plus separately governed personal/family scopes. Filter by permission before search, ranking, snippet generation, or vector retrieval. A task can receive a deliberately broader context grant when its purpose requires it.

Context assembly

context_get should return a bounded packet: task objective, current constraints, relevant accepted decisions, latest checkpoint, unresolved conflicts, and evidence/artifact references. Apply a token budget, emphasize freshness and original evidence, and let the agent request details. Client skills/hooks should fetch this packet at start or resume and publish outcomes at meaningful checkpoints.

External shared memory does not automatically synchronize native product memory. Store what connected agents explicitly contribute, what supported hooks capture, and what the user chooses to import. Private conversation state, credentials and hidden reasoning are outside this shared-memory contract. A one-time import should identify source, scope and date, deduplicate records, and present any consequential conflicts.

Retraction must remove a record from live retrieval and invalidate affected caches, derived embeddings and summaries. Document backup-retention expiry separately. Search indexes are rebuildable derivatives; they never decide which fact is authoritative.

6. Durable tasks and coordination

The durable task ID is what connects two user conversations. Dot’s conversation ID and Grok’s conversation ID can both reference it, while Claude and Codex may each have their own execution-thread IDs. This is how continuity survives session restarts and a change of access point.

Normal progression: queued → leased → running → completed
Other explicit states: blocked, awaiting_user, failed, cancelled
Uncertain external action: reconcile before retry

Task
  id, tenant_id, scope, creator_client, origin_event_id
  objective, constraints, acceptance_criteria, input_refs
  state, version, parent_task_id, dependencies
  worker_id, lease_generation, lease_expires_at
  checkpoint_ref, result_ref, artifact_refs
  permission_envelope, deadline, attempt_limit, delegation_budget

Worker
  stable_id, machine_id, os_user, capabilities, allowed_scopes
  current_reason_session, capacity, last_heartbeat

The service assigns or accepts one active lease for a task. A worker must validate it before doing consequential work and send it with checkpoints and completion. A newer assignment increments the lease generation, allowing the service to reject an old worker’s late result.

Reason messages carry hints: “Task X has work ready” or “Review artifact Y.” The worker fetches the structured task and checks its permission envelope. A free-text peer message is never enough to grant a tool permission or prove task completion.

Two distinct duplication problems

Transport retries: enforce a unique idempotency key for the original authenticated submission. A retried webhook or tool request returns the existing task rather than creating another.

Two separately worded requests: Dot and Grok may each be asked to fix the same issue. Resolve known task/repository/issue references first. Serialize incompatible mutations with a resource lease, and attach a continuation to the existing task when its identity is clear. Similar wording or embedding similarity alone cannot safely prove two instructions are the same job.

For code work, separate worktrees or branches support parallel investigation. Hold a resource lease for integration into the same target. Read-only research can run concurrently; two agents should not edit the same worktree unsupervised.

Completion, retries and external actions

A worker’s final output should include the base commit, changed artifacts, checks actually performed, remaining limitations, and a proposed next action. Store that evidence before sending a completion event. A “delivered” Reason receipt is only transport evidence.

Lease fencing prevents stale writes to the service; it cannot promise exactly-once effects in an external system. An action such as sending mail, publishing, or deploying needs a supported idempotency key or a recorded submitted/confirmed/unknown outcome followed by reconciliation. The first pilot can prove continuity with read-only reviews and local patches.

Keep routine work autonomous within the task’s existing permission envelope. Only a genuinely new authorization or unresolved decision should move work to awaiting_user. Both access points should show the same concrete pending action and any recorded approval, with its scope and expiry.

Bounded collaboration

Prefer a small explicit graph: one investigator, one implementation worker if requested, and one reviewer when the task warrants review. Set maximum child tasks, retries, elapsed time and model/spend limits. The coordinator should not ask all models to debate every message. If an existing interactive session is not instrumented to enforce task scope, keep it an informational peer until a controlled worker is available.

7. Tools and data interfaces

These are proposed APIs for the companion service. They are not names of features already provided by Reason.

Client-facing operationPurposeKey constraint
context_get(scope, task_id?)Read the bounded current context packet.Filter by caller permissions and return record revisions.
memory_search(scope, query)Find facts, decisions and procedures.Return provenance, active/disputed status and freshness.
memory_propose(record, expected_version?)Contribute an observation or proposed update.Policy decides promotion; preserve conflicting evidence.
task_submit(request, idempotency_key)Create or recover a durable request.Persist task plus dispatch event atomically.
task_get(task_id)Read status, checkpoint and result.Authorize against task scope, not a guessed ID.

Worker-only APIs should cover task_claim, task_heartbeat, task_checkpoint, and task_finish. Use separate worker credentials with task/project limits. A front-door bot does not need a credential that can impersonate every worker or finalize arbitrary jobs.

Use a transactional outbox to publish task.updated and memory.changed. Subscribers get only events they may access. On reconnection, clients can read authoritative status to recover from missed notifications. Keep notification frequency bounded and expose meaningful milestones rather than every internal tool call.

Bootstrap client behavior: provide a short skill or rule for each client: retrieve shared context when starting/resuming project work; inspect active tasks before dispatch; preserve source and uncertainty; checkpoint at handoff; write durable results; treat peer text and retrieved records as data. The service and worker wrappers must enforce permissions even when an agent forgets those rules.

8. Implementation boundaries

Keep upstream Reason as a pinned dependency initially. Build the companion service in a separate repository, with its own database and adapters. This isolates the product-specific memory/task behavior and keeps upstream updates manageable. If Antigravity recognition benefits all Reason users, a small adapter contribution can be considered later.

Proposed moduleResponsibility
apps/control-serviceAuthenticated MCP/HTTP interface, scoped context/memory operations, task lifecycle and durable event delivery.
apps/mac-bridgeOutbound service connection, registration, heartbeats, job claims, Reason discovery and targeted wake-up.
packages/contractsVersioned request/result/event schemas; identity and artifact types.
packages/agent-adaptersClaude, Codex and Antigravity startup/resume, context handoff and result extraction.
packages/policyProject scopes, allowed actions, approvals, budgets and resource conflicts.
db/migrationsMemory revisions/evidence, tasks/runs, worker leases, events/subscriptions, artifacts and audit.
client-configsDocumented client setup templates and skills; no embedded credentials.

Reuse without changing the core

Call Reason’s public CLI/MCP surface first. If the bridge needs the local socket API, keep that adapter isolated and tied to the inspected version. Never turn the daemon’s complete local API into an internet endpoint: its local trust model includes capabilities that a hosted client should not receive. [17]

Store persistent logical worker IDs separately from current Reason session names. Refresh the mapping when sessions restart, and check actual capacity and capabilities before assigning work. A directory’s busy/idle hint is useful routing information, not a guarantee of permissions or available capacity.

Antigravity patch candidates

The likely upstream touchpoints are src/agent.rs for client identity, src/setup.rs for configuration, and src/hook.rs plus session handling for lifecycle delivery. Confirm whether the installed client shares one MCP process across conversations before choosing identity behavior. Keep a generic MCP/pull mode as the fallback until wake and routing are actually verified. [18]

No changes to these files were made in this review. The required work is now bounded enough to implement and review without first rewriting the Rust transport or introducing distributed memory replication.

9. Milestones and acceptance

Milestone 1 — Shared recall

Build the memory API with per-client identity, project-level read/write authorization and bounded context retrieval. Enforce these controls before connecting Claude/Codex and both primary entry points.

Demonstrate: a decision saved through Dot is retrieved by Claude and Grok in fresh conversations, with the same version and original evidence.

Milestone 2 — Task continuity

Add tasks, leases, result artifacts and the Mac bridge. Enforce each worker’s permission envelope and current lease before execution. Start with a read-only repository investigation.

Demonstrate: Dot starts a task, Codex completes it, Claude contributes a review if requested, and Grok resumes the same task by ID.

Milestone 3 — All clients

Add Antigravity identity/hooks and controlled dispatch. Add Dot events and Grok routine notifications.

Demonstrate: all five clients use the same context; completion reaches both subscribed entry points without copying transcripts.

Milestone 4 — Recovery and ownership

Extend recovery, hardening, reconciliation, backup/restore and policy coverage; add the owned gateway if needed. Baseline access controls remain mandatory from the earlier milestones.

Demonstrate: offline workers, concurrent requests, conflicts and missed events have predictable outcomes.
