# Performance round, 2026-10-28

Measured from the Mac Studio, through `api.swarmaa.com` (Cloudflare Tunnel) and locally:

- one tool call: 4–17 ms locally, 120–180 ms through the tunnel (round trip);
- the Mac app's full refresh: 41 sequential calls, 0.38 s locally but **5.36 s through the tunnel**. The same calls in parallel take 0.62 s;
- `task_list`: rows average 12 KB and reach 24 KB (objective, result, `checkpoint.partial_output`), and one 50-row page is 463 KB;
- each `task.updated` event makes the app re-run `loadTasks` for that scope: 3 `task_list` calls, plus `bot_list`. A bot turn emits about 5 of them;
- bot turns wait 0.7–3.2 s for a worker, because bridges sleep `poll_seconds` (3) between empty claims. Then the model runs for 10–14 s (Claude Opus through the CLI, startup included).

Three parts, built in parallel. They touch different files. The contracts below are binding between them.

## Contracts

**K1. Live reply text (bridge → service).**
- While a `turn` task runs, the bridge's heartbeat checkpoint carries `partial_text`. This is the agent's reply so far as plain text, never raw JSON, at most the last 8 KB, and redacted the same way `partial_output` is.
- It is updated at least every 1.5 s while it changes.
- Claude: run turn tasks with `--output-format stream-json --verbose` and collect the assistant text deltas. The final result is parsed exactly as today.
- Codex: take the text from the `agent_message` items of `exec --json`.
- Antigravity: best effort. Omit the field if its output cannot be streamed.

**K2. Typing in `thread_read` (service → app).**
- `thread_read` returns `typing`: an array of `{task_id, agent_id, text, updated_at}`, one per **running** `turn` task in that thread whose checkpoint has a non-empty `partial_text`.
- `text` is `redactSecrets`, clipped to the last 4000 characters. The array is empty when there is nothing.

**K3. Richer `task.updated` events (service → app).**
- The `task.updated` and `task.submitted` event payloads also carry `kind`, plus `thread_id` when the task has one.

**K4. Slim `task_list` rows (service → app).**
- `task_list` rows drop `checkpoint.partial_output` and `checkpoint.partial_text`.
- They clip `objective` to 300 characters, and keep from `result` only `answer` (clipped to 500), `branch`, `changed_files`, `served`, `failure`, `check`, `summary` and `review_required`.
- `task_get` is unchanged and full.

## Part 2: service (Codex, GPT-6.1 Sol): C, K2, K3, K4

Files: `src/core/tasks.ts`, `src/core/teams.ts`, `src/core/shared.ts` if needed, `docs/API.md`, and tests.

- K4 for `task_list` (C), K2 for `thread_read`, K3 for the event payloads.
- **K5, delegation (the service side of F).**
  - When a `turn` task completes with `result.delegate.objective`, the service posts the fast reply as usual. In the same transaction it queues one follow-up `turn` for the same agent and thread, with the delegate objective, envelope `runner.model` set to the provider's full model and `runner.delegated: true`.
  - The full model is the agent's own runner model, or else Claude's `claude-opus-5-5`, carried as the constant `DELEGATE_MODEL` in `src/core/tasks.ts`.
  - A delegated turn never delegates again; ignore `delegate` on it.
  - It posts a small system notice: "<agent> handed this to <model> for a fuller answer".
  - Reuse the existing follow-up turn path in `src/core/tasks.ts` (where follow-up turns are queued after a finish) rather than a new one.
- Tests:
  - the `task_list` row size for a task with a 20 KB `partial_output` stays under 2 KB;
  - `thread_read` `typing` appears only for running turns, is redacted, and disappears when the task finishes;
  - the event payloads carry `kind` and `thread_id`;
  - delegation queues exactly one follow-up with `runner.model`, a delegated turn never delegates, and the notice is posted.
- Acceptance: `npx tsc --noEmit`, and the full suite with `node --env-file=.env.test --import tsx --test --test-concurrency=1 tests/*.test.ts`.

## Part 3: bridge (Antigravity): D, F, K1

Files: `src/bridge/worker.ts`, `src/bridge/adapters.ts`, `src/bridge/config.ts`, `tests/bridge*.test.ts` and the new tests. **Do not touch `src/bridge/sandbox.ts` or `providerEnvironment`.**

- **D.** While idle, a worker keeps one `GET /api/stream?after=now` open, using its own token and the existing client's base URL. A `task.submitted` event, or a `task.updated` with `status: "queued"`, for one of its scopes aborts `pollWait`, so it claims at once.
  - Reconnect with backoff.
  - If the stream fails, fall back to plain polling. Polling at `poll_seconds` stays as the safety net.
  - Never wake more than once per 200 ms.
- **F (bridge side), fast first reply, then delegate.**
  - Each provider's config may set `turn_model` (and `turn_effort`). For Claude it is `claude-haiku-5-5`.
  - A **non-edit** `turn` task runs with `turn_model`, unless the task's envelope sets `runner.model`, which always wins. Edit turns and patch, review and check tasks keep `model`.
  - When the fast model runs, `buildTurnPrompt` adds a short instruction. Reply now: answer directly when you can, briefly and honestly. If the request needs real work (code, research, multi-step reasoning, or anything you are unsure of), say in one line what you will do, then end your reply with a final line exactly `DELEGATE: <one-line objective>`.
  - The bridge strips that line from the answer, and returns it as `result.delegate = { objective }`, clipped to 500 characters.
  - It never emits `delegate` for a task whose envelope already names a model.
- **K1** as specified above.
- Tests:
  - a fake stream wakes the worker within 300 ms;
  - stream loss falls back to polling;
  - `turn_model` is chosen only for non-edit turns without a runner model;
  - a `DELEGATE:` line becomes `result.delegate` and is stripped from the answer;
  - stream-json parsing yields `partial_text`, and the final answer is unchanged.
- Acceptance: `npx tsc --noEmit`, and the full suite as above.
