## Ranked findings and concrete proposed fixes

1. **Tenant-wide Teams lock limits independent posting.** Twenty tenants deliver 1522.701 posts/s versus 511.415 in one tenant (2.977×). Same-tenant lock p95 is 14.965 ms versus 0.003 ms spread out. Batches alternate order to reduce time drift. **Fix:** replace the tenant-only Teams key with ordered thread/agent/swarm keys; acquire every affected key for multi-object turn actions in a single consistent order. Review atomicity and deadlock ordering before changing it.

2. **Swarm workers queue on the task-scope lock, ahead of Teams.** Twenty-step total p50 is 235.697 ms. Task-scope acquisition p50/p95 is 20.112/41.484 ms; Teams p95 is only 0.003 ms. Across ten runs, summed task-scope acquisition is 8058.082 ms and Teams is 0.445 ms (overlapping worker waits, not wall time). **Fix:** shorten the scope-wide task critical section and fence independent work with agent/resource leases and worker-slot rows; preserve claim/finish lock order. Narrowing Teams alone will not improve this path.

3. **SSE latency follows the fixed idle poll.** Commit-ack-to-arrival p50/p95 is 102.585/202.938 ms. Replaying 1,000 real events takes p50 424.050 ms. **Fix:** wake the existing events SELECT on transactional LISTEN/NOTIFY and immediately drain full batches instead of sleeping 10 ms per batch; retain durable events and the xmin/cursor no-skip predicate. These are separate latency and catch-up improvements, not missing-data repairs.

4. **Sidebar status has an N+1 query cost.** agent_list executes 78 SELECTs for 50 agents (including authentication, status/worker checks and sections). HTTP p95 is 10.649 ms. **Fix:** batch running-task status by agent ids and live-worker availability by scope, then join/map once; retain the indexed unread-count query. An additional messages index does not remove these round trips.

5. **Attention can use purpose-built ordered partial indexes as history grows.** HTTP p95 is 34.494 ms; the captured plans below separate database execution from HTTP time. **Fix candidates:** `CREATE INDEX tasks_attention_failed ON tasks (tenant_id, scope, updated_at DESC) WHERE status='failed' AND resolved_at IS NULL;` and `CREATE INDEX tasks_attention_review ON tasks (tenant_id, scope, updated_at DESC) WHERE status='completed' AND resolved_at IS NULL AND kind IN ('patch','turn') AND (result->>'review_required')::boolean IS TRUE AND result->>'head_commit' IS NOT NULL;`. Re-measure before attributing HTTP tails to SQL: this run does not establish either index as a measured win.

6. **Sequential-scan audit:** claim-mixed-1000/4 contains a planned scan on messages/tasks/swarm_steps; see actual loops above. The non-flow fixture can leave the claim sibling subplan unexecuted (0 loops), so a planned scan is not evidence of runtime table scanning. **Conditional fix for the sibling lookup:** `CREATE INDEX tasks_flow_unhealthy ON tasks (flow_id) WHERE flow_id IS NOT NULL AND status IN ('blocked','failed','cancelled');`. The existing tasks_flow_step index already leads with flow_id; validate with representative nonempty flows before adding a redundant index. Thread reads and swarm-step lookup already use messages_thread_seq_idx and swarm_steps_swarm_idx; no new index is justified there.

All fixes are proposals only. Source/migrations are unchanged. Synthetic task fixtures, fake worker execution and small warm-cache plans do not validate real provider latency, long production histories, cold storage, remote TLS or question-answer/reassignment correctness. No full CI, commit, push, restart or deployment was performed. Next action: coordinator reviews the lock changes first, then validates chosen fixes with this benchmark and focused concurrency tests.
