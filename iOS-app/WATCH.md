# Apple Watch companion

The Watch uses the paired iPhone's existing Swarmaa connection. Credentials remain on the phone and Mac. WatchConnectivity can defer delivery until the devices are available; open the apps to refresh. Bot threads use the same server data as the Mac. The bounded Watch snapshot shows up to 20 bots from the phone's first 100 results, up to five abbreviated text messages per bot and up to 20 open structured questions from the first 100 results. Long messages end in an ellipsis; full question details are either shown completely or replaced with an unavailable marker. Structured bot questions remain read-only on Watch and are answered on iPhone; they are separate from transactions.

## Voice memos

Choose a bot before recording. Watch records original M4A files with explicit start and stop, up to 15 minutes, 20 memos and 20 MiB per file. Recording ends when the app becomes inactive (including a lowered wrist) or an interruption occurs; it does not continue in the background. A partial file is retained when possible. Memos transfer as files to iPhone, then in bounded chunks to the Mac using the same memo ID, hash and chosen bot thread. iPhone storage is available in Files and the You menu. Phone receipt means only that iPhone saved it; a Mac receipt is shown only after the service returns a matching stored hash and size. Delivery can remain unconfirmed after a timeout; retry preserves the file and destination. Older phone memos without a destination require choosing a bot in You before upload. Deleting an unconfirmed copy requires explicit confirmation. The Mac stores memos in the configured `SWARMAA_MEMO_DIR` or `~/.swarmaa/memos`; see `docs/WATCH-HOST.md` for host prerequisites and retention.

## Transactions

Transactions are a separate Watch screen; normal chat and bot questions never create financial transactions. Choose a bot, enter payee, decimal amount, currency, date and category, and explicitly request a preview. Updating requires the exact existing expense ID. The Watch displays the server's complete account, operation, before and after fields and expiry; if the review exceeds its payload limit, confirmation is unavailable on Watch. The second screen repeats those details and requires a separate Confirm tap. A pending confirmation keeps the same confirmation ID across retries; a timeout remains unconfirmed until a matching receipt is obtained. A confirmed preview replay is accepted only when its receipt matches the original persisted confirmation; if that confirmation is unavailable, the result stays unconfirmed and no new confirmation ID is invented. The Watch reports Ledger updated only after matching the receipt's confirmation, review, account and expense fields. Server integration and RetireOdds configuration are required; see `docs/WATCH-HOST.md`. Sign-out invalidates drafts for the old connection. The server's expiry and atomic preconditions govern delayed confirmations.

## Paired-device review

Before release, verify microphone permission denial, interruption and relaunch, file transfer offline and after a lost receipt, stable destination, chunk resume, storage limits, Files access and explicit deletion. Test phone and Watch account switching with delayed transfers. For transactions, verify exact create and update previews, complete before/after fields, an explicit second confirmation, expiry, changed ledgers, replay of the same confirmation ID, lost replies, account isolation and receipt mismatches against a disposable test ledger. Check absent integration configuration and oversized reviews. Verify regular chat and structured bot questions never execute transactions. Exercise accessibility text and navigation on actual paired devices.

This change has not been built or tested on a simulator or device.
